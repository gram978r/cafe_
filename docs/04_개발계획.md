# 개발 계획

## 1. 전체 작업 순서와 나눈 이유

이 계획은 4시간 실습 중 구현과 사용자 확인에 배정된 100분을 기준으로 한다. 예상 시간은 추정치이며, 데이터 오류를 숨기거나 화면만 만드는 방식으로 시간을 줄이지 않는다.

작업 순서는 다음과 같다.

1. **EPIC 1 — 저장 기반과 샘플 데이터 연결**
   - 로그인한 운영자가 실제 저장 데이터에 접근할 수 있는 기반을 만든다.
   - 이후 모든 기능이 같은 매장 자료를 사용하도록 데이터 연결과 저장 방식을 먼저 확인한다.
2. **EPIC 2 — 판매 기록과 기간별 실적**
   - 판매 기록을 입력·수정·삭제하고, 그 결과를 일·주·월 실적 화면에서 확인한다.
   - 수익성·손익·재료 잔량 계산의 공통 원천인 판매 데이터를 먼저 완성한다.
3. **EPIC 3 — 수익성·손익·재료 잔량 연결**
   - 앞 단계의 판매 기록과 기존 원가·비용·재고 자료를 연결한다.
   - 같은 판매 변경이 메뉴 수익성, 손익, 재료 잔량에 반영되는지 최종 핵심 흐름으로 확인한다.

### 전체 규모와 예상 시간

| 구분 | 작업·사용자 확인 예상 | Story 수 |
|---|---:|---:|
| EPIC 1 | 20분 | 1개 |
| EPIC 2 | 40분 | 2개 |
| EPIC 3 | 35분 | 3개 |
| 예비 시간 | 5분 | - |
| **합계** | **100분** | **6개** |

예상 시간에는 구현, 자동 검사, 실제 화면에서의 사용자 확인을 포함한다.

## 2. 공통 구현 조건

모든 Story에 다음 조건을 적용한다.

- PRD의 수업 중 구현 범위만 대상으로 한다. 비용 직접 입력, 엑셀 가져오기·내보내기, 재고 입고·폐기 직접 입력, 발주량 참고, 분기·반기·연간 조회, 예상 손익, 백업·복원은 수업 후 확장으로 둔다.
- 실제 데이터베이스에 저장하고, 새로고침 후에도 저장한 결과가 남아야 한다. 화면에 고정한 가짜 배열이나 임시 브라우저 저장만으로 완료하지 않는다.
- 서버에서도 입력값을 다시 검사한다. 필수값 누락, 잘못된 날짜, 숫자가 아닌 값, 음수, 할인액이 매출액보다 큰 경우를 저장하지 않는다.
- 기존 자료의 주의사항을 지킨다.
  - 금액은 원자료 기준 원화(KRW), 부가세 제외로 표시한다.
  - 재료 단위는 g, ml, 개를 구분한다.
  - 빈 값과 0은 다르게 처리한다.
  - 2026-09-19~2026-09-30처럼 자료가 완결되지 않은 기간을 판매 0으로 단정하지 않는다.
  - 월별 계획과 일별 비용을 같은 비용으로 중복 합산하지 않는다.
  - 원자료가 일·메뉴·채널별 집계라는 점을 유지하고 주문 건수로 해석하지 않는다.
- TRD의 기술 조건을 구현 계획에 반영한다.
  - Supabase PostgreSQL(관계형 데이터베이스)을 저장소로 사용하고, 변경 작업은 마이그레이션(데이터 구조 변경 기록)으로 관리한다.
  - Supabase Auth(로그인)와 RLS(사용자별 데이터 접근 제한)를 적용한다.
  - 입력 검사와 계산은 서버 경로에서도 수행하며, 관련 저장 변경은 하나의 작업 단위로 처리한다.
  - GitHub에 변경 이력을 저장하고, Vercel에서 미리보기 배포와 운영 배포를 확인한다.
  - 비밀 키와 운영 개인정보를 코드와 저장소에 넣지 않는다.
  - 단위 테스트(Vitest)와 핵심 사용자 흐름 테스트(Playwright)를 작성하고, 화면 확인 전에 자동 검사를 통과시킨다.
- 시간 부족 시 먼저 줄이는 것은 수업 후 기능과 디자인 시안의 내보내기·인쇄 같은 부가 기능이다. 계산 정확성, 데이터 저장, 기본 오류 처리, 검증, 핵심 연결 흐름은 줄이지 않는다.

## 3. EPIC 1 — 저장 기반과 샘플 데이터 연결

**상태: 완료 (자동 검사 및 사용자 화면 확인 완료)**

### 목적

카페 운영자가 로그인 후 Prep Cafe의 실제 저장 자료를 조회하고, 이후 입력한 판매 기록을 같은 저장소에서 다시 읽을 수 있게 한다.

### 포함 Story

#### Story 1. 운영자로 접속해 저장된 매장 자료를 조회한다

**사용자가 할 수 있는 일**

- 운영자 계정으로 프로그램에 접속한다.
- Prep Cafe의 판매·메뉴·레시피·비용·재고 자료가 연결된 화면을 연다.
- 화면을 새로고침해도 같은 자료를 다시 조회한다.

**자동 검사**

- 로그인하지 않은 사용자는 매장 자료를 조회할 수 없는지 확인한다.
- 메뉴, 레시피, 비용, 재고, 판매 자료의 식별자가 서로 연결되는지 확인한다.
- g, ml, 개 단위가 섞여서 합산되지 않는지 확인한다.
- 빈 값과 숫자 0이 구분되는지 확인한다.
- 원자료를 반복해 연결하거나 초기화해도 같은 자료가 중복 생성되지 않는지 확인한다.
- RLS로 다른 사용자나 다른 매장의 자료가 조회되지 않는지 확인한다.

**내가 화면에서 확인할 행동과 예상 결과**

1. 로그인 화면에서 운영자 계정으로 접속한다.
2. 판매 기록 화면에서 기존 메뉴와 날짜를 확인한다.
3. 새로고침한다.
4. 같은 메뉴·날짜·금액 자료가 다시 보이고, 로그인 상태와 접근 권한이 유지된다.

**완료 기준**

- 화면의 자료가 실제 저장 데이터에서 조회된다.
- 새로고침 후 데이터가 유지된다.
- 이후 EPIC 2와 EPIC 3이 같은 매장 자료를 사용한다.
- 데이터베이스 마이그레이션, 인증, 접근 제한, 기본 자동 검사가 통과한다.

## 4. EPIC 2 — 판매 기록과 기간별 실적

**상태: 완료 (자동 검사 및 사용자 화면 확인 완료)**

### 목적

판매 기록을 실제로 변경하고, 변경 결과가 일·주·월 실적에 정확히 반영되게 한다.

### 포함 Story

#### Story 2. 판매 기록을 입력·수정·삭제한다

**사용자가 할 수 있는 일**

- 판매 관리 화면에서 날짜, 메뉴, 채널, 판매 수량, 단가, 할인액을 입력한다.
- 채널은 시안의 `매장(홀)`, `포장(To-Go)`, `배달(Delivery)` 중 하나를 선택한다.
- 저장한 기록을 수정하거나 삭제한다.
- 저장 결과를 판매 목록에서 다시 확인한다.

**자동 검사**

- 날짜, 메뉴, 채널, 수량, 단가 등 필수값이 없으면 저장하지 않는다.
- 수량과 금액이 숫자이며 음수가 아닌지 확인한다.
- 할인액이 총 판매액보다 크면 저장하지 않는다.
- 서버에서도 같은 검사를 수행해 화면 검사를 우회한 저장을 막는다.
- 저장·수정·삭제가 부분적으로만 적용되지 않도록 처리한다.
- 수정·삭제 후 관련 실적 계산의 원천 데이터가 즉시 바뀌는지 확인한다.

**내가 화면에서 확인할 행동과 예상 결과**

1. 예시로 아메리카노를 2개, 단가 4,500원, 할인 500원으로 입력한다.
2. 판매액은 `2 × 4,500 - 500 = 8,500원`으로 표시된다.
3. 같은 기록의 수량을 3개로 수정하면 판매액은 `3 × 4,500 - 500 = 13,000원`으로 바뀐다.
4. 기록을 삭제하면 목록과 해당 기간 실적에서 그 기록이 사라진다.
5. 새로고침해도 입력·수정 결과가 유지된다.

**완료 기준**

- 입력·수정·삭제가 실제 저장 데이터에 반영된다.
- 잘못된 값은 저장되지 않고 사용자가 수정할 수 있는 오류 안내를 본다.
- 판매액 계산 결과가 FRD의 기준과 일치한다.
- 다음 Story의 일·주·월 실적이 이 Story의 변경 결과를 사용한다.

#### Story 3. 일·주·월별 실적을 조회한다

**사용자가 할 수 있는 일**

- 성과 화면에서 일·주·월을 선택한다.
- 이전 기간, 다음 기간, 오늘 기간으로 이동한다.
- 전체·영업일·휴무일 또는 시안에서 제공하는 기간 필터를 사용한다.
- 선택 기간의 판매액, 판매 수량, 메뉴별 실적을 확인한다.

**자동 검사**

- 일 조회는 해당 날짜, 주 조회는 월요일부터 일요일, 월 조회는 해당 월의 경계를 정확히 사용한다.
- 날짜 경계 밖의 판매가 합산되지 않는지 확인한다.
- 판매 기록을 추가·수정·삭제하면 일·주·월 합계가 함께 바뀌는지 확인한다.
- 휴무일과 판매 0일을 구분한다.
- 2026-09-19~2026-09-30처럼 아직 완결되지 않은 날짜를 확정된 판매 0으로 표시하지 않는다.
- 데이터가 없는 기간과 실제 0원인 기간을 구분한다.

**내가 화면에서 확인할 행동과 예상 결과**

1. 월요일 실적 100,000원과 화요일 실적 80,000원이 있는 기간을 주간 조회한다.
2. 주간 합계가 `100,000 + 80,000 = 180,000원`으로 표시된다.
3. 월간 조회로 바꾸면 해당 월의 모든 날짜가 포함된다.
4. Story 2의 판매 기록을 수정하면 일·주·월 화면의 합계가 동시에 바뀐다.
5. 새로고침 후 선택 기간과 저장된 판매 결과를 다시 확인한다.

**완료 기준**

- 일·주·월 조회가 동작한다.
- 판매 CRUD(입력·수정·삭제)와 기간별 실적이 연결된다.
- 기간 경계, 미완결 날짜, 휴무일, 빈 값·0 처리가 자동 검사와 화면 확인을 통과한다.

## 5. EPIC 3 — 수익성·손익·재료 잔량 연결

**상태: 완료 (자동 검사 및 사용자 화면 확인 완료)**

### 목적

같은 판매 기록을 바탕으로 메뉴별 변동 수익성, 실제 손익, 재료 잔량을 한 흐름에서 확인한다. 변동 수익성은 판매량에 따라 함께 변하는 비용을 뺀 값이다.

### 포함 Story

#### Story 4. 메뉴별 변동 수익성을 확인한다

**사용자가 할 수 있는 일**

- 수익성 화면에서 기간, 채널, 메뉴를 선택한다.
- 메뉴별 순매출, 식재료비, 포장비, 결제수수료, 변동 수익성을 확인한다.
- 레시피 원가 상세 또는 원가 미입력 상태를 확인한다.

**자동 검사**

- 판매 스냅샷에 저장된 판매가, 할인, 순매출, 결제수수료, 단위 식재료비·포장비를 우선 사용한다.
- 변동 수익성에서 고정비를 메뉴별로 임의 배분하지 않는다.
- 레시피 또는 단가가 비어 있으면 원가를 0으로 속이지 않고 `원가 미입력` 또는 계산 보류 상태로 표시한다.
- 포장비는 포장 판매에만 적용하고, 빈 채널 레시피는 전체 채널 적용 규칙을 따른다.
- 판매 기록 변경 후 해당 메뉴와 기간의 수익성이 다시 계산된다.

**내가 화면에서 확인할 행동과 예상 결과**

1. 순매출 8,500원, 식재료비 2,000원, 포장비 200원, 결제수수료 170원을 가진 메뉴를 조회한다.
2. 변동 수익성이 `8,500 - 2,000 - 200 - 170 = 6,130원`으로 표시된다.
3. 원가가 비어 있는 메뉴는 0원 수익성이 아니라 `원가 미입력` 상태로 표시된다.
4. Story 2에서 판매 수량을 수정한 뒤 같은 메뉴의 결과가 바뀌는지 확인한다.
5. 새로고침 후 선택 기간과 계산 결과가 유지된다.

**완료 기준**

- 메뉴별 변동 수익성 계산이 FRD 기준과 일치한다.
- 고정비를 잘못 배분하지 않는다.
- 원가 미입력·채널별 원가·포장비 규칙이 구분된다.
- 판매 기록 변경과 새로고침 후 결과가 일관된다.

#### Story 5. 기간별 실제 손익을 확인한다

**사용자가 할 수 있는 일**

- 손익 화면에서 일·주·월 기간을 선택한다.
- 순매출, 변동비, 고정비, 실제 손익을 확인한다.
- 비용 상세 영역을 펼쳐 손익에 포함된 비용을 확인한다.

**자동 검사**

- 실제 손익은 선택 기간의 순매출에서 해당 기간의 식재료비·포장비·결제수수료와 실제 비용을 차감한다.
- 월별 계획 금액과 일별 비용을 같은 비용으로 중복 합산하지 않는다.
- 비용이 비어 있으면 0으로 임의 확정하지 않고 상태를 표시한다.
- 선택 기간 밖의 비용과 매출은 손익에 포함하지 않는다.
- Story 2의 판매 변경과 Story 4의 원가 결과가 손익에 반영되는지 확인한다.

**내가 화면에서 확인할 행동과 예상 결과**

1. 순매출 8,500원, 식재료비 2,000원, 포장비 200원, 결제수수료 170원, 실제 비용 3,000원을 가진 기간을 조회한다.
2. 실제 손익이 `8,500 - (2,000 + 200 + 170) - 3,000 = 3,130원`으로 표시된다.
3. 같은 기간의 월별 계획 금액과 일별 비용이 함께 있는 경우 한 번만 반영되는지 확인한다.
4. 판매 기록을 수정한 뒤 손익이 다시 계산되는지 확인한다.
5. 새로고침 후 손익 결과와 기간 선택이 유지된다.

**완료 기준**

- 실제 손익이 기간별로 조회된다.
- 변동비·실제 비용·월별 계획과 일별 비용의 중복 처리가 FRD 기준과 일치한다.
- 비용 누락·기간 경계·판매 변경을 자동 검사한다.

#### Story 6. 재료 잔량과 실사 차이를 확인한다

**사용자가 할 수 있는 일**

- 재고 화면에서 재료별 단위와 잔량을 확인한다.
- 전체 재료, 차이 있음, 정상 상태 필터를 사용한다.
- 기초 재고, 입고, 폐기, 판매 사용량, 계산 잔량, 최근 실사 수량을 비교한다.

**자동 검사**

- 계산 잔량은 재료 단위별로 분리한다.
- 기존 재고 이벤트의 입고·폐기·조정과 판매 시 레시피 사용량을 중복 반영하지 않는다.
- 레시피나 단위가 비어 있으면 잔량을 확정하지 않고 확인 필요 상태를 표시한다.
- 실사 수량이 있으면 계산 잔량과 차이를 구분해 표시한다.
- 미완결 미래 날짜의 판매를 재고 사용량에 확정 반영하지 않는다.

**내가 화면에서 확인할 행동과 예상 결과**

1. 어떤 재료의 기초 재고가 10개이고, 입고 5개, 폐기 1개, 판매 사용량 3개인 상태를 조회한다.
2. 계산 잔량이 `10 + 5 - 1 - 3 = 11개`로 표시된다.
3. 실사 수량 10개가 있으면 차이가 `10 - 11 = -1개`로 표시된다.
4. 단위가 g인 재료와 ml인 재료가 서로 합쳐지지 않는지 확인한다.
5. Story 2의 판매 수량을 수정한 뒤 판매 사용량과 계산 잔량이 함께 바뀌는지 확인한다.
6. 새로고침 후 재료 잔량과 실사 차이가 유지된다.

**완료 기준**

- 재료별 잔량, 실사 수량, 차이 상태를 조회할 수 있다.
- 입고·폐기·판매 사용량의 부호와 단위가 정확하다.
- 원가·레시피·판매 데이터가 부족한 경우 임의의 0이 아니라 확인 필요 상태를 보여준다.
- 판매 기록 입력부터 실적 → 메뉴 수익성 → 실제 손익 → 재료 잔량까지 연결된 흐름을 실제 화면에서 시연할 수 있다.

## 6. 최종 사용자 확인 시나리오

다음 순서로 하나의 판매 기록이 전체 화면에 연결되는지 확인한다.

1. 운영자로 로그인한다.
2. 판매 관리에서 아메리카노 2개, 단가 4,500원, 할인 500원을 입력한다.
3. 판매액 8,500원이 판매 목록과 일별 실적에 나타나는지 확인한다.
4. 주간·월간 조회로 바꾸어 같은 판매가 기간 합계에 포함되는지 확인한다.
5. 수익성 화면에서 `8,500 - 2,000 - 200 - 170 = 6,130원`을 확인한다.
6. 손익 화면에서 실제 비용 3,000원을 포함한 `3,130원`을 확인한다.
7. 재고 화면에서 해당 판매의 레시피 사용량이 잔량에 반영되는지 확인한다.
8. 판매 수량을 3개로 수정하고 3~7번의 관련 결과가 함께 바뀌는지 확인한다.
9. 새로고침 후 모든 변경 결과가 유지되는지 확인한다.
10. 잘못된 할인액이나 음수 수량을 입력해 저장이 거부되고 오류 안내가 나타나는지 확인한다.

## 7. 수업 후 확장 기능

아래 기능은 이번 100분 구현 범위와 완료 조건에서 제외한다.

- 일별 비용과 월별 비용의 직접 입력·수정·삭제
- 엑셀 양식 내려받기와 엑셀·JSON 기록 가져오기, 중복 가져오기 검증 화면
- 판매·비용·재고 원장의 엑셀 내보내기와 인쇄
- 재료 입고·폐기·재고 조정 직접 입력
- 재고 실사 입력, 실사 차이 원인 보고서, 부족 재료의 발주량 참고
- 분기·반기·연간 조회
- 예상 손익과 목표 달성률·전주 대비 증감률·영업이익률 등 기준이 추가로 필요한 지표
- 고정비를 메뉴나 기간에 배분하는 분석
- 백업 파일 생성, 백업 복원, 복원 전 미리보기와 충돌 처리
- 다중 사용자 역할, 다중 매장, 상세 권한 관리
- 시안에 있는 날씨·피크타임 등 외부 또는 추가 데이터 기반 분석
