# 프렙 카페 운영 분석 시스템 기술 요구사항 문서

## 문서 범위

이 문서는 `docs/01_PRD.md`, `docs/02_FRD.md`와 `design` 폴더의 시안을 구현하기 위한 기술 기준을 정한다. PRD와 FRD의 기능, 사용 순서, 계산 기준은 바꾸지 않는다.

수업 중 핵심 흐름은 다음과 같다.

> 판매 기록 입력·수정·삭제 → 일·주·월 실적 조회 → 메뉴별 변동 수익성 → 실제 손익·재료 잔량

수업 후 기능은 같은 구조로 확장할 수 있도록 데이터와 파일 경계를 미리 마련하되, 초기 구현의 완료 기준에는 포함하지 않는다.

## 사용할 기술과 선택 이유

### 기본 기술 구성

| 영역 | 선택 기술 | 선택 이유 |
|---|---|---|
| 웹 애플리케이션 | Next.js App Router | 화면 이동, 공통 레이아웃, 서버 처리와 배포 구성을 한 프로젝트에서 관리한다. |
| 프로그래밍 언어 | TypeScript | 날짜·금액·수량·단위를 잘못 연결하는 오류를 개발 단계에서 줄인다. |
| 화면 스타일 | Tailwind CSS와 시안 디자인 토큰 | 시안의 색상, 글꼴, 간격, 반응형 규칙을 재사용한다. |
| 데이터베이스 | Supabase PostgreSQL | 판매·메뉴·레시피·재고·비용처럼 서로 연결된 자료를 관계형 구조로 저장한다. |
| 로그인·접근 제어 | Supabase Auth와 PostgreSQL RLS | 로그인 사용자와 매장별 데이터 접근을 제한한다. RLS는 데이터베이스 행 단위 접근 규칙이다. |
| 데이터 접근 | Supabase 서버 클라이언트와 SQL 마이그레이션 | 데이터베이스 구조 변경을 기록하고, 서버에서 일관된 조회·저장을 수행한다. |
| 입력 검증 | Zod 기반 스키마 검증 | 화면 입력과 엑셀·JSON 열의 형식과 필수값을 같은 기준으로 검증한다. |
| 엑셀 처리 | SheetJS 계열의 서버 처리 라이브러리 | 엑셀 양식 읽기와 리포트 파일 생성을 처리한다. |
| 테스트 | Vitest와 Playwright | 계산 단위와 실제 화면 흐름을 각각 검사한다. |
| 코드 보관 | GitHub | 코드, 데이터베이스 변경 기록, 리뷰와 되돌리기를 관리한다. |
| 운영 배포 | Vercel | GitHub 변경과 연결해 미리보기와 운영 배포를 만든다. |

Next.js App Router는 파일 구조 기반 라우팅과 공통 레이아웃을 제공한다. [Next.js App Router 공식 문서](https://nextjs.org/docs/app)

### 기술 선택의 원칙

- 운영 원자료와 계산 결과를 코드에 하드코딩하지 않는다.
- 화면은 입력과 표시를 담당하고, 계산 기준은 서버의 공통 도메인 계산 모듈과 데이터베이스 조회에서 한 번만 정의한다.
- 작은 단일 매장 데이터셋에는 별도 분석 플랫폼이나 메시지 큐를 추가하지 않는다.
- 시안의 따뜻한 색상·타이포그래피·반응형 구성을 스타일 토큰으로 관리하며, 특정 화면에 색상값을 반복해서 넣지 않는다.
- GitHub에는 코드와 스키마·샘플 데이터만 보관하고 실제 운영 데이터와 비밀값은 보관하지 않는다.

### 데이터베이스 선택과 비용

Supabase PostgreSQL을 사용한다. Supabase는 PostgreSQL 데이터베이스를 제공하고, 데이터베이스 백업과 RLS를 지원한다. [Supabase 데이터베이스 문서](https://supabase.com/docs/guides/database/overview)

- 개발·수업 환경은 가장 작은 사용량의 플랜부터 시작한다.
- 운영에서 자동 백업 기간과 시점 복구가 필요하면 해당 기능을 제공하는 유료 플랜을 검토한다.
- 현재 기록량과 단일 매장 사용량은 관계형 데이터베이스 한 곳으로 충분하다.
- 사용량이 늘기 전까지 별도의 캐시 서버, 검색 서버, 분석 웨어하우스를 추가하지 않는다.
- 실제 요금은 배포 시점의 Vercel·Supabase 요금표로 확인한다.

## 처리 순서

### 공통 요청 처리

1. 사용자가 화면에서 입력하거나 파일을 선택한다.
2. 브라우저에서 형식과 기본 범위를 먼저 검사한다.
3. 서버에서 같은 검사를 다시 수행한다. 브라우저 검사는 사용성용이고, 서버 검사가 최종 기준이다.
4. 서버가 로그인 사용자와 매장 접근 권한을 확인한다.
5. 데이터베이스 트랜잭션으로 원본 기록과 필요한 스냅샷을 함께 저장한다. 트랜잭션은 여러 저장 작업이 모두 성공하거나 모두 취소되게 하는 처리다.
6. 저장이 완료되면 화면이 최신 기록을 다시 조회한다.
7. 계산 결과는 원본 기록과 같은 기간·메뉴·채널 조건으로 다시 집계한다.
8. 계산 자료가 없으면 0으로 바꾸지 않고 계산 보류 상태와 원인을 반환한다.

### 판매 기록 처리

1. 판매일자, 메뉴, 매장·포장·배달 채널, 판매수량, 단가, 할인금액을 받는다.
2. 수량·단가·할인금액을 검증한다.
3. 순매출을 계산한다.
4. 입력 시점의 레시피·재료가격 기준을 찾아 식재료 원가와 포장 원가를 산출한다.
5. 결제 수수료 기준이 있으면 반영하고, 없으면 수수료 계산 보류 상태를 저장한다.
6. 판매 당시의 식재료 원가·포장 원가·수수료 스냅샷을 판매 기록에 저장한다. 스냅샷은 당시 값을 보존한 복사본이다.
7. 실적·수익성·손익·재고 조회가 같은 판매 기록을 참조한다.

### 조회·계산 처리

- 일·주·월 탭은 기간 조건만 바꾸고 공통 집계 함수를 사용한다.
- 주간 기간은 월요일부터 일요일까지로 만든다.
- 영업 달력의 영업 여부와 마감 여부를 판매 기록과 함께 읽는다.
- 2026-09-19부터 2026-09-30까지의 미완성 날짜는 확정된 판매 0으로 만들지 않는다.
- 메뉴 수익성은 순매출에서 식재료 원가·포장 원가·결제 수수료를 뺀 변동 수익성 기준을 사용한다.
- 실제 손익은 판매 원가와 날짜별 비용기록을 반영하고, 월비용계획을 같은 비용으로 중복 반영하지 않는다.
- 재료 잔량은 재료별 단위로 계산하며, g·ml·개를 서로 합산하지 않는다.
- 최신 실사수량은 계산상 잔량과 별도 값으로 보관하고 차이를 표시한다.

### 파일 처리

1. 사용자가 엑셀 또는 JSON 파일을 선택한다.
2. 파일 형식, 자료 버전, 열 이름, 날짜, 단위, 필수 ID를 검사한다.
3. 임시 영역에서 전체 파일을 먼저 검증한다.
4. 오류 행과 중복 후보를 사용자에게 보여준다.
5. 사용자가 반영을 선택하면 한 번의 트랜잭션으로 저장한다.
6. 반영 후 성공 건수, 제외 건수, 오류 사유를 표시한다.
7. 엑셀과 JSON이 같은 원자료이면 두 번째 가져오기를 중복으로 경고한다.

## 주요 파일이 맡는 일

아래 구조는 기능을 나누는 기준이다. 실제 파일명은 개발 시작 시 이 구조를 유지해 만든다.

```text
app/
  (dashboard)/
    sales/page.tsx              판매 기록 관리 화면
    performance/page.tsx        일·주·월 실적 화면
    profitability/page.tsx      메뉴별 변동 수익성 화면
    pnl-inventory/page.tsx      실제 손익·재료 잔량 화면
  api/
    sales/route.ts              판매 조회·입력·수정·삭제 요청
    reports/route.ts            엑셀·리포트·인쇄용 자료 요청
    imports/route.ts            엑셀·JSON 검증·가져오기 요청
    backups/route.ts            백업·복원 요청
components/
  navigation/                   공통 메뉴와 매장·영업 상태
  sales/                        판매 표, 입력 모달, 채널 필터
  performance/                  기간 탭, 기간 이동, 요약 카드, 일자 표
  profitability/                메뉴 필터, 원가 상세, 수익성 표
  inventory/                    재고 표, 실사 입력, 차이 상태
  common/                       버튼, 입력칸, 오류·빈 상태·확인 모달
lib/
  domain/calculations/           순매출, 수익성, 손익, 재고 계산
  domain/validation/            화면·파일 공통 검증 규칙
  data/                          데이터베이스 조회와 저장 함수
  imports/                       엑셀·JSON 읽기, 매핑, 중복 검사
  exports/                       엑셀·리포트·백업 파일 생성
  auth/                           로그인·매장 접근 확인
  errors/                         사용자 메시지와 내부 오류 기록
supabase/
  migrations/                    데이터베이스 구조 변경 기록
  seed/                          가상 샘플 데이터 입력 자료
tests/
  unit/                          계산·검증 테스트
  integration/                   데이터베이스·가져오기 테스트
  e2e/                           화면 핵심 흐름 테스트
```

실제 프로젝트에는 비밀값을 담은 `.env` 파일과 운영 데이터 파일을 커밋하지 않는다.

## 데이터 저장·이동·복구

### 데이터베이스 구조

기존 JSON의 자료 종류를 다음 테이블로 옮긴다.

- `stores`, `store_members`: 매장과 사용자 접근 범위
- `suppliers`: 공급사
- `materials`: 재료와 단위, 구매 용량, 납기·안전재고 일수
- `menus`: 메뉴와 분류, 판매 기준가, 레시피 버전
- `recipes`: 메뉴별 재료 사용량과 적용 채널
- `material_price_history`: 적용 시작일별 구매가격·구매용량
- `business_calendar`: 영업 여부, 마감 여부, 날씨, 메모
- `sales`: 판매일자·메뉴·채널·수량·단가·할인·순매출·당시 원가 스냅샷
- `opening_inventory`: 첫 영업 시작 전 재고
- `inventory_events`: 입고·폐기·실사조정과 사유·공급사·실사수량
- `expenses`: 날짜별 실제 비용
- `monthly_expense_plans`: 월별 비용 계획
- `dataset_metadata`: 자료 출처, 버전, 기준일, 통화, 금액 기준
- `import_batches`, `import_errors`: 가져오기 단위와 오류 기록
- `backup_metadata`: 백업 시점, 자료 버전, 행 수, 검증 상태

모든 업무 테이블에는 매장 ID와 안정적인 원본 ID를 둔다. 금액은 원화 정수 금액으로 저장하고, 수량은 원자료의 단위를 함께 저장한다. 날짜는 날짜 값으로 저장하며 화면 표시 형식과 계산 기준을 분리한다.

### 저장 규칙

- 판매 당시 단가·할인·순매출·수수료·식재료 원가·포장 원가를 판매 행에 보관한다.
- 원재료 가격이나 레시피가 나중에 바뀌어도 과거 판매의 수익성이 바뀌지 않게 한다.
- 빈칸, 0, 계산 보류를 서로 다른 상태로 저장한다.
- 삭제는 기본적으로 사용자 확인 후 처리하고, 집계에서 사라지는 원본 ID를 기록한다.
- 가져오기와 복원은 임시 검증 후 일괄 반영한다.
- 집계 결과는 원본 기록에서 다시 만들 수 있도록 별도 수기 결과를 저장하지 않는다.

### 백업과 복원

두 겹으로 운영한다.

1. **데이터베이스 제공자 백업**: Supabase의 관리형 백업을 사용한다. 유료 플랜에서는 일일 백업과 특정 시점 복구를 사용할 수 있다. [Supabase 백업 문서](https://supabase.com/docs/guides/platform/backups)
2. **앱 백업 파일**: 사용자가 전체 업무 자료와 메타데이터를 JSON 백업 파일로 내려받는다. 파일에는 스키마 버전, 생성 시각, 매장 ID, 행 수와 검증용 해시를 넣는다.

복원 절차는 다음과 같다.

- 백업 파일을 임시 영역에서 읽는다.
- 매장 ID, 스키마 버전, 필수 테이블, ID 중복, 단위와 날짜를 검사한다.
- 복원 전 현재 데이터베이스 백업을 남긴다.
- 검증을 통과한 파일만 트랜잭션으로 반영한다.
- 실패하면 기존 데이터베이스를 유지한다.
- 성공하면 복원 시각과 행 수를 기록하고 집계 결과를 다시 확인한다.

데이터베이스 백업은 데이터베이스에 저장된 자료를 보호하지만, 별도 파일 저장소의 객체까지 자동으로 복원하지 않을 수 있으므로 앱 백업 파일에는 필요한 운영 자료를 함께 담는다.

## 정보 보호

### 로그인과 접근 제어

- 운영 배포는 Supabase Auth 로그인이 있어야 접근할 수 있게 한다.
- 초기 버전은 한 매장의 운영 관리자 역할만 제공한다. 다중 권한과 다중 매장은 확장하지 않는다.
- 모든 업무 테이블에 `store_id`를 두고 사용자의 매장 소속을 확인한다.
- PostgreSQL RLS를 모든 외부 노출 테이블에 적용한다. Supabase는 RLS와 데이터베이스 권한을 함께 구성하도록 안내한다. [Supabase RLS 문서](https://supabase.com/docs/guides/database/postgres/row-level-security)
- 서비스 전용 비밀키는 서버에서만 사용하고 브라우저에 전달하지 않는다.

### 개인정보와 비밀값

- 현재 원자료의 가상 매장·운영 기록만 저장한다.
- 고객 이름, 전화번호, 주소, 결제수단 번호와 같은 개인정보는 저장하지 않는다.
- 시안의 담당자명과 프로필 이미지는 예시 표시로 취급하고 실제 개인정보 입력 기능을 만들지 않는다.
- GitHub에 `.env`, 운영 백업, 실제 고객 자료, 데이터베이스 접속 문자열을 커밋하지 않는다.
- Vercel 환경변수에 개발·미리보기·운영 값을 분리해 등록한다. Vercel 환경변수는 코드와 분리해 저장되고 환경별로 적용할 수 있다. [Vercel 환경변수 문서](https://vercel.com/docs/environment-variables)
- 모든 운영 통신은 HTTPS를 사용한다.

### 가져오기·내보내기 보호

- 업로드 파일의 확장자만 믿지 않고 실제 파일 구조와 열을 검사한다.
- 업로드한 파일을 브라우저에 그대로 실행하거나 다른 사용자에게 공개하지 않는다.
- 리포트와 백업 파일은 로그인한 사용자의 요청에서만 생성한다.
- 다운로드 파일명에 매장명·기간을 넣되, 개인정보나 비밀값은 넣지 않는다.
- 로그에는 금액·수량·ID 등 운영 오류 해결에 필요한 최소 정보만 남긴다.

## 오류 대응

### 오류 종류별 처리

| 오류 종류 | 처리 방법 |
|---|---|
| 입력 오류 | 저장 전 필드 아래에 쉬운 설명을 표시하고 저장하지 않는다. |
| 계산 자료 누락 | 계산 보류와 누락된 자료명을 표시한다. 0으로 숨기지 않는다. |
| 자료 없음 | “기록 없음”을 표시하고 실제 0과 구분한다. |
| 날짜·기간 오류 | 시작일과 종료일, 마감 상태, 자료 기준일을 다시 확인한다. |
| 단위 불일치 | g·ml·개를 섞지 않고 해당 행을 보류한다. |
| 중복 기록 | 원본 ID와 날짜·메뉴·채널을 비교해 중복 후보를 표시한다. |
| 데이터베이스 오류 | 사용자에게 재시도 가능한 메시지를 보여주고 상세 내용은 서버 로그에 남긴다. |
| 동시 수정 | 마지막 저장 시점과 현재 자료가 다르면 덮어쓰지 않고 다시 불러오기를 안내한다. |
| 파일 오류 | 전체 파일을 먼저 검증하고, 반영 전 오류 행과 사유를 보여준다. |
| 복원 오류 | 기존 자료를 유지하고 복원 실패 이유를 표시한다. |
| 배포 오류 | Vercel 미리보기에서 차단하고 운영 배포를 진행하지 않는다. |

### 일관성 보장

- 판매 저장과 스냅샷 저장은 하나의 트랜잭션으로 처리한다.
- 파일 가져오기는 부분 성공을 기본값으로 사용하지 않고, 검토 후 일괄 반영한다.
- 손익·수익성·재고 집계는 저장된 원본을 다시 조회해 계산한다.
- 오류 메시지는 사용자용 설명과 내부 추적용 오류 ID를 분리한다.
- 반복 요청으로 중복 저장되지 않도록 요청 ID 또는 안정적인 원본 ID를 사용한다.

## 배포 방법

### GitHub 저장소

- `main`: 운영 배포 기준 브랜치
- 작업 브랜치: 기능 단위 변경
- Pull Request: 코드 검토와 자동 검사 단위
- `README`: 실행 방법, 환경변수 이름, 데이터 가져오기와 복구 방법
- `docs`: PRD, FRD, TRD, 운영·복구 안내
- `supabase/migrations`: 데이터베이스 변경 이력
- 실제 운영 데이터와 비밀값은 저장소에서 제외

### Vercel 환경

- GitHub 저장소를 Vercel 프로젝트에 연결한다.
- 작업 브랜치와 Pull Request에는 Preview 배포를 만든다.
- `main` 병합 시 Production 배포를 만든다.
- 개발·Preview·Production의 Vercel 환경변수와 Supabase 프로젝트를 분리한다.
- 데이터베이스 마이그레이션이 성공한 뒤 애플리케이션 배포를 확정한다.
- 배포 실패 시 이전 정상 배포로 되돌릴 수 있게 운영 배포를 보존한다.

Vercel은 연결된 Git 저장소의 커밋과 Pull Request를 기준으로 미리보기 및 운영 배포를 만들 수 있다. [Vercel Git 배포 문서](https://vercel.com/docs/deployments/overview)

### 속도와 비용 기준

- 판매 목록은 기간·채널·메뉴 조건을 데이터베이스에서 먼저 적용하고 필요한 행만 가져온다.
- 긴 목록은 페이지 단위로 조회한다.
- 집계 조건에 필요한 날짜, 매장, 메뉴, 채널 ID에 데이터베이스 인덱스를 둔다. 인덱스는 검색용 정렬표다.
- 메뉴·재료·레시피처럼 변경이 적은 기준자료는 요청 사이에 재사용할 수 있지만, 판매·비용·재고 결과는 최신 저장 후 다시 조회한다.
- 초기 목표는 제공된 전체 샘플 자료로 핵심 화면이 일반적인 네트워크에서 2초 안에 표시되고, 전체 샘플 가져오기가 30초 안에 완료되는 것이다. 측정 결과에 따라 조정한다.
- 초기 사용량은 Vercel과 Supabase의 소규모 플랜에서 시작하고, 데이터베이스 저장량·요청량·백업 요구가 요금제 한도를 넘을 때만 상위 플랜을 검토한다.
- 대량 분석, 실시간 POS 연동, 다중 매장, 대규모 파일 저장은 현재 기술 범위에 포함하지 않는다.

## 확인 방법

### 자동 검사

- 순매출, 메뉴 변동 수익성, 실제 손익, 재료 잔량의 작은 숫자 계산을 단위 테스트한다.
- 빈칸과 0, 음수, 할인 초과, 원가 누락, 비용 누락을 검사한다.
- 월요일 시작 주간, 월초·월말, 자료 시작일·마감일을 검사한다.
- g·ml·개 혼합 계산이 차단되는지 검사한다.
- 엑셀·JSON 열 누락, 날짜 오류, 단위 오류, 중복 ID를 검사한다.
- 데이터베이스 권한과 매장별 RLS가 허용·차단해야 할 행을 각각 검사한다.

### 화면 흐름 검사

1. 로그인한다.
2. 판매 기록을 새로 저장한다.
3. 판매 기록을 수정하고 삭제한다.
4. 일·주·월 실적에서 변경 결과를 확인한다.
5. 메뉴별 수익성에서 원가와 수수료를 확인한다.
6. 실제 손익에서 비용 중복이 없는지 확인한다.
7. 재료 잔량에서 계산상 잔량과 실사수량을 비교한다.
8. 새로고침 후 저장 결과가 유지되는지 확인한다.

### 가져오기·복구 검사

- 정상 엑셀, 정상 JSON, 열 누락 파일, 단위 오류 파일, 중복 파일을 각각 테스트한다.
- 가져오기 실패 후 기존 자료가 바뀌지 않는지 확인한다.
- 백업 후 자료를 수정하고 복원해 원래 집계가 돌아오는지 확인한다.
- 잘못된 백업 파일 복원 시 기존 자료가 유지되는지 확인한다.

### 배포 검사

- Pull Request에서 Preview 배포가 생성되는지 확인한다.
- Preview가 Production 데이터베이스를 사용하지 않는지 확인한다.
- `main` 병합 후 Production 배포가 생성되는지 확인한다.
- 비밀값이 빌드 로그·브라우저·GitHub 저장소에 노출되지 않는지 확인한다.
- 배포 실패 시 직전 정상 배포로 복귀할 수 있는지 확인한다.
